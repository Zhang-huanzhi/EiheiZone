# V1.2 / 002 公网访问性能诊断报告

## 1. 前言与排查范围

在 `V1.2 / 001` 中，系统性能瓶颈已初步收敛至 **“中国大陆客户端访问海外源站的跨境公网路径”**。本轮诊断旨在深入传输层与网络层，通过 ICMP Ping、路由追踪（Tracert）、应用层抓包（DevTools/F12）、服务器内核参数审计等多维度交叉取证，彻底查清链路各阶段的性能损耗成因。

- **基础设施已执行调整**：
  - 关闭 Cloudflare 代理（切回 DNS Only 模式）。
  - 服务器 TCP 拥塞控制算法由 `cubic` 调整为 `bbr`。
- **排查边界**：未修改 `backend/`、`frontend/` 业务代码，未对 Next.js RSC 及动态鉴权数据配置激进缓存。

---

## 2. 核心诊断结论（Executive Summary）

1. **链路物理底座恶化（高 RTT + 波动丢包）**：
   大陆直连腾讯云韩国源站存在 **~300ms 的异常高底座延迟**，且伴随 **3.7% ~ 14.0% 的动态丢包**。路由显示延迟突变发生在进入源站云网关交接点，证实瓶颈在**跨境公网互联质量**而非服务器算力过载。
2. **应用传输层产生“队头阻塞”（Head-of-Line Blocking）**：
   前端采用 HTTP/2 多路复用（所有 RSC 请求共用单条 TCP 连接）。在无丢包时传输高效，但一旦遭遇公网丢包，**单一连接阻塞导致 13+ 个并发 RSC 请求集体挂起**，将毫秒级抖动放大为数十秒的长尾卡顿。
3. **架构优化方向明确**：
   - **BBR**：已实施，属单机传输层“减震”，无法改变物理绕路。
   - **边缘加速 / 线路迁移**：改变数据包物理路径的唯一“治本”手段。

---

## 3. 多维证据链小结

### 3.1 Ping 连通性测试（高 RTT 确定，丢包具时间波动）
目标 IP：`150.109.241.217`（腾讯云首尔二区）

| 样本发包量 | 丢包数 | 丢包率 | 最短 / 最长 RTT | 平均 RTT | 网络特征定性 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **50 包** | 7 | **14.0%** | 287ms / 368ms | **299ms** | 短时高频脉冲丢包 |
| **200 包** | 14 | **7.0%** | 286ms / 369ms | **297ms** | 中度网络抖动 |
| **500 包** | 21 | **4.2%** | 285ms / 423ms | **300ms** | 链路常态丢包 |
| **1000 包** | 37 | **3.7%** | 284ms / 483ms | **297ms** | 长周期基准丢包 |

> **数据洞察**：长周期基准丢包率为 **3.7%（37/1000）**，短周期突发可达 **14%**。结合近 300ms 的基准 RTT，表明跨境链路处于高抖动、弱网状态。

---

### 3.2 路由追踪（路径存在显著延迟跳变）
命令：`tracert -d 150.109.241.217`

```text
第 1~7  跳: 【国内骨干网】   本地电信局域/省网骨干 ───────────> 8ms (极快)
第 8~11 跳: 【国际出口】     电信出口防火墙/网关 ─────────────> (* * * ICMP限速)
第 12~14跳: 【韩国运营商】   韩国电信骨干网 (KT) ─────────────> 75ms (物理光纤正常)
──────────────────────────【关键跳变点：第 15 跳】──────────────────────────
第 15   跳: 【互联接入点】   218.145.43.22 ───────────────────> 265ms 💥
第 20   跳: 【腾讯云源站】   150.109.241.217 ─────────────────> 299ms
```

> **数据洞察**：大陆到韩国本地运营商物理光缆仅需 **75ms**；进入源站机房入口交接时延迟骤增至 **265ms+**。证实普通公网互联未做直连优化，存在跨洋或次优路径调度。

---

### 3.3 传输层与内核参数审计

* **F12 协议抓包（HTTP/2 多路复用生效）**：
  * 所有 `_rsc` 接口 `Protocol = h2`，且共享一致的 `Connection ID`。
  * **影响**：连接复用免去了多次握手开销；但在 TCP 层面，任何分包丢失都会阻塞整条管道内所有并发流。
* **内核拥塞控制算法（已由 CUBIC 切换为 BBR）**：
  * **原状态**：`net.ipv4.tcp_congestion_control = cubic`（遭遇丢包时窗口减半，RTO 指数退避，严重拖慢重传）。
  * **现状态**：已配置并激活 `BBR`（基于模型测算带宽与延迟，大幅降低弱网丢包对吞吐量的惩罚）。

---

### 3.4 端到端场景对照测试

| 测试场景 | 典型响应时间 | 核心现象与成因 |
| :--- | :--- | :--- |
| **开启 VPN（专线）** | **0.5s ~ 1.5s** | 走企业级跨境直连通道，规避公网绕路与丢包，HTTP/2 性能发挥极致。 |
| **直连 + 关闭 CF** | **数秒 ~ 10s+** | 受制于 300ms 物理 RTT 及丢包重传。 |
| **直连 + 开启 CF 免费版** | **数十秒 ~ 接近 1min** | 国内访问被 Anycast 调度至美西节点，形成“跨太平洋两次”的负优化。 |

## 4. 根因链机制图解

综合上述证据，用户侧感知的极端长尾延迟由以下链条逐级放大形成：

```text
   [ 物理网络层 ] 
   大陆客户端 ──(公网绕路 300ms RTT + 3.7%~14% 丢包)──> 韩国服务器
                          │
                          ▼ 触发 TCP 分包丢失
   [ 内核传输层 ] 
   传统 CUBIC 算法触发超时重传惩罚（RTO 翻倍等待）
                          │
                          ▼ 单一 TCP 管道挂起
   [ 应用协议层 ] 
   Next.js 13+ 个并发 RSC 请求被 HTTP/2 队头阻塞（Connection ID 共享）
                          │
                          ▼ 浏览器等待最慢分片
   [ 表现层结果 ] 
   前端页面处于 Pending 状态，整体耗时拉长至数十秒甚至 1 分钟
```

## 5. 优化方案与演进矩阵

根据实施成本、架构改造成本与加速效果，建议采取分阶段推进策略：

```
                    [ 长期根治 / 极速体验 ]
                               ▲
                               │  ● 方案 B: 迁移至香港/优质专线源站 (30ms)
                               │  ● 方案 A: 接入 EdgeOne 边缘加速 (30~50ms)
       性能收益 (Latency)      │
                               │  ● 方案 C: 开启 HTTP/3 (QUIC) 协议
                               │  ● [已执行] 开启 BBR 算法
                               │
                               ┼────────────────────────────────────────►
                             低成本 / 零改动                     高实施度 / 架构迁移
                                               工程投入 (Effort)
```

### 方案对比与实施建议

| 方案类别 | 具体措施 | 预期收益 | 实施成本 | 适用阶段 |
| :--- | :--- | :--- | :---: | :---: |
| **传输层优化**<br>*(已落地)* | **开启 Google BBR 算法**<br>`sysctl net.ipv4.tcp_congestion_control=bbr` | 提升丢包下的重传效率，降低吞吐断崖风险。 | **零成本**<br>(已完成) | **当前阶段** |
| **边缘网络加速**<br>*(推荐方案)* | **接入腾讯云 EdgeOne / 亚太 CDN**<br>客户端 $\to$ 边缘节点(30ms) $\to$ 内网回源韩国。 | 彻底规避公网绕路，静态资源就近秒开，抹平跨境丢包。 | **低**<br>(配置 CNAME 即可) | **短期首选**<br>(不想搬迁源站) |
| **源站基础设施**<br>*(彻底根治)* | **迁移至香港轻量 / 优质直连机房**<br>替换为 CN2 GIA / AS9929 优化线路实例。 | 物理 RTT 降至 **30ms~50ms**，丢包率趋近 **0%**。 | **中**<br>(需数据迁移/重新部署) | **中期演进** |
| **协议层演进**<br>*(补充手段)* | **全站启用 HTTP/3 (QUIC)**<br>Web 服务端（Nginx 1.25+/Caddy）开启 UDP 传输。 | 彻底根除 HTTP/2 的 TCP 队头阻塞问题。 | **低~中**<br>(需升级 Web 服务组件) | **持续优化** |
| **应用层保护**<br>*(兜底防护)* | **Next.js RSC 请求聚合 & 超时降级**<br>减少前端碎片化请求并发，设置接口兜底状态。 | 缩短阻塞等待范围，提升弱网下的 UI 可用性。 | **中**<br>(需修改业务代码) | **后续迭代** |
