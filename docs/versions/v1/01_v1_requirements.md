## 2. 项目背景


随着个人学习、生活和发展阶段的变化，项目创建者与家人的沟通方式可能逐渐从高频即时聊天，转向更需要长期记录、集中查看和结构化沉淀的信息同步方式。传统的即时通讯工具虽然可以满足日常聊天，但不适合长期、结构化地沉淀生活近况、常见问题和重要支出信息。

项目创建者本人也不习惯使用 QQ、微信朋友圈等社交型工具来同步个人生活状态，因此希望建立一个由自己控制的个人家庭门户系统，用于向家人稳定地同步学习、生活和阶段变化中的重要信息。

本项目同时也是一个长期个人开发项目。通过从需求分析、架构设计、后端开发、前端开发、测试到部署的完整流程，项目创建者可以系统性地学习 Web 后端开发与现代工程实践，并将项目作为个人作品集的一部分持续维护。

因此，本项目不仅是一个家庭沟通工具，也承担以下目标：

- 降低重复沟通成本；
- 提高家人获取近况和重要信息的便利性；
- 将家庭问答和重大支出信息结构化保存；
- 形成一个可长期迭代、可展示工程能力的真实项目。

## 3. 产品定位

Personal Family Portal 是一个面向个人与家庭成员的轻量级家庭门户系统。

它的核心用途是：由项目创建者主动维护一个稳定的信息空间，用于向家人同步生活近况、沉淀家庭问答、记录重大资金支出，并在合适的权限范围内提供可查看、可回溯的信息入口。

本产品不是通用社交平台，也不是完整记账系统，而是一个围绕个人生活透明、家庭沟通和长期信息沉淀设计的私域 Web 应用。

在 V1 阶段，本产品重点关注以下方向：

- 以 Post 承载生活近况和轻量状态同步；
- 以 QA 承载家人问题与长期可回看的回答；
- 以 Expenditures 承载重大资金支出记录；
- 以 Dashboard 为家人提供集中查看入口；
- 以公开首页展示项目基本信息和部分公开内容。

本产品同时具备个人作品集属性。项目将尽量按照真实 Web 项目的开发流程推进，包括需求定义、设计、实现、测试和部署，以展示项目创建者的产品理解、后端能力和工程实践能力。

## 4. V1 目标

V1 阶段的目标是完成 Personal Family Portal 的最小可用版本，建立清晰的产品边界、基础权限模型和核心业务流程，为后续功能扩展和长期维护打下基础。

V1 不追求功能复杂度，而是优先保证核心场景可以闭环运行：项目创建者能够发布近况、回答 QA、记录重大支出；Family 和 Owner 能够登录后集中查看相关信息并提交问题；公开访客只能访问允许公开的内容。

V1 阶段需要达成以下目标：

- 建立基础账号与权限机制，区分公开访客、家人用户和项目创建者；
- 支持生活近况 Post 的创建、展示和可见范围控制；
- 支持家庭 QA 的提问、回答和状态管理；
- 支持重大支出 Expenditures 的记录和查看；
- 提供家人首页 Dashboard，用于集中展示最近近况、问答和支出信息；
- 提供公开首页，用于展示项目基本信息和部分公开内容；
- 提供项目创建者基础管理区，用于管理 Post、QA 和 Expenditures；
- 形成一套可继续扩展的基础工程结构；
- 为后续设计、开发、测试和部署提供明确依据。

## 5. 用户角色

V1 阶段系统包含三类用户角色：公开访客、家人用户和项目创建者。

| 角色 | 英文标识 | 是否需要登录 | 角色说明 |
|---|---|---:|---|
| 公开访客 | Public | 否 | 未登录用户，只能访问公开首页和公开内容 |
| 家人用户 | Family | 是 | 受邀家人，登录后可以查看家人可见内容，并提交问题 |
| 项目创建者 | Owner | 是 | 系统所有者，负责发布近况、提出和回答问题、记录支出和管理内容 |

### 5.1 公开访客 Public

公开访客是未登录用户。

公开访客只能访问系统允许公开展示的内容，例如公开首页、项目介绍和被设置为公开可见的 Post。公开访客不能查看家人可见内容，不能提交问题，不能查看重大支出记录，也不能进行任何内容管理操作。

### 5.2 家人用户 Family

家人用户是项目创建者授权访问系统的家庭成员。

家人用户登录后可以查看家人可见的生活近况、家庭问答和重大支出记录。家人用户可以提交问题，用于向项目创建者询问生活、学习、资金使用或其他关心事项。

V1 阶段，家人用户不具备内容管理权限，不能发布 Post，不能回答 QA，不能创建或修改支出记录。

### 5.3 项目创建者 Owner

项目创建者是系统的主要维护者和内容发布者。

项目创建者可以创建、编辑和删除 Post；可以提交问题，也可以查看并回答 Family 或 Owner 提交的问题；可以创建、编辑和删除重大支出记录；可以管理内容的可见范围。

V1 阶段，项目创建者是唯一具备内容管理权限的角色。

## 6. V1 功能范围

V1 阶段聚焦于 Personal Family Portal 的核心闭环功能，主要包括账号与权限、近况分享、家庭问答、重大支出记录、家人首页、公开首页和项目创建者基础管理区七个模块。

### 6.1 账号与权限

系统需要支持基础登录能力，并根据用户角色控制可访问内容和可执行操作。

V1 阶段至少需要区分以下访问身份：

- 公开访客；
- 家人用户；
- 项目创建者。

不同身份在系统中拥有不同权限。公开访客只能访问公开内容；Family 和 Owner 可以访问家人可见内容并提交问题；项目创建者可以管理 Post、QA 和 Expenditures。

### 6.2 Post 近况分享

Post 用于承载项目创建者的生活近况、阶段性状态和轻量信息同步。

V1 阶段，项目创建者可以创建、编辑和删除 Post。Post 需要支持可见范围控制，至少包括公开可见和仅家人可见两种范围。

家人用户可以查看公开 Post 和仅家人可见 Post。公开访客只能查看公开 Post。

### 6.3 QA 家庭问答

QA 用于沉淀家人关心的问题和项目创建者的回答，避免重要问题散落在即时通讯记录中。

V1 阶段，Family 和 Owner 可以提交问题。项目创建者可以查看问题、回答问题，并管理问题状态。

QA 至少应支持以下状态：

- 未回答；
- 已回答。

### 6.4 Expenditures 重大支出记录

Expenditures 用于记录重大资金支出，增强资金使用的透明度和可回溯性。

V1 阶段，项目创建者可以创建、编辑和删除重大支出记录。支出记录应至少包含支出日期、金额、币种、分类和说明。

家人用户可以查看重大支出记录。公开访客默认不能查看重大支出记录。

### 6.5 家人首页 Dashboard

家人首页用于为家人提供集中查看入口，减少信息分散带来的查找成本。

V1 阶段，家人首页应展示以下内容：

- 最近发布的 Post；
- 最近的 QA 内容或待回答问题；
- 最近的重大支出记录。

### 6.6 公开首页 Public Home

公开首页用于向未登录访客展示项目的基本信息，以及允许公开展示的内容。

V1 阶段，公开首页应包含项目简介，并展示公开 Post 或公开 Post 入口。公开首页不得展示仅家人可见内容、QA 详情或重大支出记录。

### 6.7 项目创建者基础管理区 Owner Workspace

项目创建者基础管理区用于支持项目创建者完成 V1 阶段的核心内容管理操作。

V1 阶段，项目创建者可以通过基础管理区完成以下操作：

- 创建、编辑和删除 Post；
- 查看 Family 和 Owner 提交的 QA；
- 回答 QA 并管理 QA 状态；
- 创建、编辑和删除重大支出记录。

基础管理区仅面向项目创建者开放。公开访客和家人用户不能访问基础管理区。

V1 阶段的基础管理区只服务于 Post、QA 和 Expenditures 的内容管理，不提供用户管理页面、审计日志、角色权限配置或系统配置能力。


## 7. V1 不做范围

V1 阶段以完成核心业务闭环为目标，不追求功能完整度和社交复杂度。以下内容不纳入 V1 开发范围。

### 7.1 不做原生 App

V1 只实现 Web 应用，不开发 iOS、Android 或桌面客户端。

移动端访问可以通过浏览器适配解决，但不单独开发原生 App。

### 7.2 不做复杂朋友圈功能

V1 的 Post 只用于项目创建者向家人同步近况，不做通用社交平台能力。

V1 不支持以下功能：

- 点赞；
- 评论区；
- 转发；
- 关注关系；
- 好友关系；
- 动态推荐流。

### 7.3 不做即时聊天

V1 不实现实时聊天或私信功能。

家庭沟通中的即时交流仍然可以通过现有通讯工具完成。本系统只负责沉淀适合长期保存和集中查看的信息。

### 7.4 不做完整记账系统

V1 的 Expenditures 只记录重大支出，不做完整个人财务管理。

V1 不支持以下功能：

- 日常小额流水；
- 预算管理；
- 收入管理；
- 多账户管理；
- 自动账单导入；
- 财务报表分析。

### 7.5 不做复杂搜索

V1 不实现全文搜索、高级筛选或复杂排序。

如有必要，V1 可以只提供基础列表展示。搜索能力放入后续版本考虑。

### 7.6 不做 AI 与向量检索

V1 不接入 AI 能力，不使用 pgvector，不实现智能问答、语义搜索或自动总结。

AI 相关能力可以在核心数据积累稳定后，作为后续增强功能加入。

### 7.7 不做复杂通知

V1 不实现邮件通知、短信通知、微信通知或 App 推送。

用户需要主动登录系统查看更新。通知能力可以在后续版本中根据实际使用情况决定是否加入。

### 7.8 不做文件上传

V1 暂不实现本地文件上传、图片上传、附件上传或凭证上传。

如需要图片内容，V1 可以先通过纯文本描述完成近况同步。文件上传能力放入后续版本设计。

### 7.9 不做多语言

V1 默认使用中文界面和中文内容，不实现中英日多语言切换。

多语言能力可以在项目进入公开展示或实际使用需求明确后再考虑。

### 7.10 不做复杂后台管理系统

V1 不开发复杂 Admin 后台，但需要提供面向项目创建者的基础管理区，用于完成 Post、QA 和 Expenditures 的核心内容管理。

V1 不提供用户管理页面。家人用户账号由项目创建者通过初始化数据或服务器手动 SQL 方式创建和维护。更复杂的用户管理、审计日志、角色自定义、权限组配置、后台配置中心等能力不纳入 V1。

## 8. 核心使用场景

本节描述 V1 阶段需要支持的核心使用场景。核心使用场景用于帮助明确系统的主要业务闭环，并为后续功能设计、页面设计和测试用例提供依据。

### 8.1 项目创建者发布生活近况

项目创建者希望向家人同步近期生活、学习或其他重要状态时，可以在系统中发布一条 Post。

Post 可以根据内容性质设置不同可见范围：

- 适合公开展示的内容，可以设置为公开可见；
- 只适合家人查看的内容，可以设置为仅家人可见。

发布完成后，家人用户可以在家人首页或 Post 列表中查看相关近况。公开访客只能查看公开可见的 Post。

### 8.2 家人查看近期信息

家人用户登录系统后，可以通过家人首页集中查看项目创建者最近更新的信息。

家人首页应帮助家人快速了解以下内容：

- 最近发布的生活近况；
- 最近的家庭问答；
- 最近记录的重大支出。

该场景的目标是减少信息分散带来的查找成本，让家人不需要从多段聊天记录中反复翻找重要信息。

### 8.3 Family 或 Owner 提交问题，项目创建者回答

Family 或 Owner 在关心某个问题时，可以在 QA 模块中提交问题。

问题可以与生活、学习、资金使用、计划安排或其他家庭关心事项相关。问题提交后，项目创建者可以查看该问题，并在合适时间进行回答。

回答完成后，该问题状态变为已回答，Family 和 Owner 用户可以再次查看问题和回答内容。

该场景的目标是将重复性问题和重要回答沉淀下来，形成长期可回看的家庭问答记录。

### 8.4 项目创建者记录重大支出

当发生需要向家人说明的重大资金支出时，项目创建者可以在 Expenditures 模块中记录该支出。

支出记录应至少包含以下信息：

- 支出日期；
- 支出金额；
- 币种；
- 支出分类；
- 支出说明。

家人用户登录后可以查看重大支出记录。公开访客默认不能查看重大支出记录。

该场景的目标是增强重大资金使用的透明度，同时避免将支出信息散落在即时通讯记录中。

### 8.5 公开访客查看公开首页

未登录的公开访客可以访问公开首页。

公开首页用于展示项目的基本介绍，以及允许公开展示的内容。公开访客可以查看公开首页和公开 Post，但不能访问家人可见内容、QA 内容和重大支出记录。

该场景的目标是让项目具备一定作品集展示属性，同时保证家庭信息和敏感信息不会对外暴露。

### 8.6 项目创建者进行内容管理

项目创建者登录后，可以进入基础管理区，对 V1 阶段的核心内容进行管理。

基础管理区应支持项目创建者完成以下操作：

- 发布、编辑和删除 Post；
- 查看 Family 和 Owner 提交的问题；
- 回答问题并更新 QA 状态；
- 创建、编辑和删除重大支出记录。

该场景的目标是让项目创建者能够通过正常产品界面维护核心内容，而不是依赖直接操作数据库完成日常内容管理。

## 9. 功能需求

功能需求优先级定义如下：

- P0：V1 必须完成，否则 V1 核心闭环不成立；
- P1：V1 优先考虑，但在开发时间不足时可以延后到 V1.1。

## 10. 权限需求

本节定义 V1 阶段不同用户角色的访问权限和操作权限。权限需求是后续系统设计、接口设计和测试验证的核心依据之一。

V1 阶段系统包含三类访问身份：

- 公开访客 Public；
- 家人用户 Family；
- 项目创建者 Owner。

### 10.1 权限矩阵

| 功能 / 内容          | Public 公开访客 | Family 家人用户 | Owner 项目创建者 |
| ---------------- | ----------: | ----------: | ----------: |
| 访问公开首页           |          可以 |          可以 |          可以 |
| 查看项目基本介绍         |          可以 |          可以 |          可以 |
| 查看公开 Post        |          可以 |          可以 |          可以 |
| 查看仅家人可见 Post     |         不可以 |          可以 |          可以 |
| 创建 Post          |         不可以 |         不可以 |          可以 |
| 编辑 Post          |         不可以 |         不可以 |          可以 |
| 删除 Post          |         不可以 |         不可以 |          可以 |
| 查看 QA 内容         |         不可以 |          可以 |          可以 |
| 提交 QA 问题         |         不可以 |          可以 |          可以 |
| 回答 QA 问题         |         不可以 |         不可以 |          可以 |
| 管理 QA 状态         |         不可以 |         不可以 |          可以 |
| 查看重大支出记录         |         不可以 |          可以 |          可以 |
| 创建重大支出记录         |         不可以 |         不可以 |          可以 |
| 编辑重大支出记录         |         不可以 |         不可以 |          可以 |
| 删除重大支出记录         |         不可以 |         不可以 |          可以 |
| 访问家人首页 Dashboard |         不可以 |          可以 |          可以 |
| 访问 Owner 基础管理区    |         不可以 |         不可以 |          可以 |
| 管理用户             |         不可以 |         不可以 |         不可以 |

### 10.2 默认权限规则

V1 阶段遵循以下默认权限规则：

- 未登录用户默认为 Public；
- 登录后的家人用户为 Family；
- 项目创建者为 Owner；
- 未明确标记为公开的内容，不应对 Public 展示；
- 重大支出记录默认仅 Family 和 Owner 可见；
- QA 内容默认仅 Family 和 Owner 可见；
- 内容管理操作默认仅 Owner 可执行；
- Owner 基础管理区仅 Owner 可以访问；
- V1 不提供用户管理页面，用户账号通过初始化数据或服务器手动 SQL 方式维护。

### 10.3 访问控制要求

系统应在页面访问和数据访问两个层面同时进行权限控制。

页面访问层面：

- Public 访问家人首页时，应被阻止；
- Public 访问内容管理页面时，应被阻止；
- Family 访问内容管理页面时，应被阻止；
- Public 和 Family 访问 Owner 基础管理区时，应被阻止；
- 未授权访问不应展示受保护页面内容。

数据访问层面：

- Public 请求仅家人可见内容时，不应返回具体数据；
- Public 请求 QA 或 Expenditures 数据时，不应返回具体数据；
- Family 请求 Owner 专属管理能力时，应被拒绝；
- Owner 可以访问并管理 V1 范围内的全部业务数据。

### 10.4 权限验证要求

V1 阶段应对核心权限场景进行验证，至少包括：

- Public 不能查看仅家人可见 Post；
- Public 不能查看 QA 内容；
- Public 不能查看重大支出记录；
- Family 不能创建、编辑或删除 Post；
- Family 不能回答 QA；
- Family 不能创建、编辑或删除重大支出记录；
- Public 和 Family 不能访问 Owner 基础管理区；
- Owner 可以管理 Post、QA 和 Expenditures；
- Dashboard 展示内容必须符合当前用户权限。

## 11. 数据需求

本节定义 V1 阶段系统需要保存和使用的核心业务数据。数据需求只描述业务上需要记录哪些信息，不定义具体数据库表结构、字段类型、索引或关联关系。

### 11.1 用户数据

系统需要保存用于登录、身份识别和权限判断的用户数据。

V1 阶段包含两类需要登录的用户：

- 家人用户 Family；
- 项目创建者 Owner。

公开访客 Public 不需要在系统中保存为用户数据。

用户数据至少应包含以下信息：

- 用户标识；
- 登录账号；
- 显示名称；
- 用户角色；
- 登录凭证；
- 账号状态；
- 创建时间；
- 更新时间。

V1 阶段不提供用户管理页面。家人用户账号由项目创建者通过初始化数据或服务器手动 SQL 方式创建和维护。

### 11.2 Post 数据

Post 用于保存项目创建者发布的生活近况和状态同步内容。

Post 数据至少应包含以下信息：

- Post 标识；
- 标题；
- 正文内容；
- 可见范围；
- 创建时间；
- 更新时间。

Post 的可见范围至少包括：

- 公开可见；
- 仅家人可见。

公开访客只能查看公开可见的 Post。家人用户和项目创建者可以查看公开可见和仅家人可见的 Post。

### 11.3 QA 数据

QA 用于保存 Family 或 Owner 提出的问题和项目创建者的回答。

QA 数据至少应包含以下信息：

- QA 标识；
- 问题内容；
- 提问人；
- 回答内容；
- 回答人；
- QA 状态；
- 创建时间；
- 更新时间；
- 回答时间。

QA 状态至少包括：

- 未回答；
- 已回答。

QA 内容默认仅家人用户和项目创建者可见，不向公开访客展示。

### 11.4 Expenditures 数据

Expenditures 用于保存重大资金支出记录。

支出数据至少应包含以下信息：

- 支出记录标识；
- 支出日期；
- 金额；
- 币种；
- 支出分类；
- 支出说明；
- 创建时间；
- 更新时间。

支出记录默认仅家人用户和项目创建者可见，不向公开访客展示。

V1 阶段的支出记录不保存以下敏感信息：

- 银行卡号；
- 完整交易流水号；
- 详细住址；
- 身份证件信息；
- 其他不适合长期保存或展示的敏感信息。

### 11.5 Dashboard 展示数据

家人首页 Dashboard 不产生独立业务数据，而是聚合展示系统中已有的数据。

Dashboard 至少应聚合展示：

- 最近发布的 Post；
- 最近的 QA 内容或待回答问题；
- 最近的重大支出记录。

Dashboard 展示内容必须遵守当前用户的权限范围，不得向未授权用户展示受保护数据。

### 11.6 数据时间信息

V1 阶段的核心业务数据应记录必要的时间信息，用于排序、展示和后续追踪。

至少以下数据需要记录创建时间和更新时间：

- 用户数据；
- Post；
- QA；
- Expenditures。

其中 QA 还应记录回答时间，Expenditures 还应记录实际支出日期。

## 12. 非功能需求

本节定义 V1 阶段除具体业务功能之外的系统质量要求。V1 阶段的非功能需求以安全、隐私、可维护、可测试和可部署为重点，不追求复杂架构或高并发能力。

### 12.1 权限安全

系统必须保证不同用户角色只能访问其权限范围内的内容。

V1 阶段至少需要满足以下要求：

- 未登录用户不能访问家人首页；
- 未登录用户不能查看仅家人可见 Post；
- 未登录用户不能查看 QA 内容；
- 未登录用户不能查看重大支出记录；
- 家人用户不能访问项目创建者的内容管理功能；
- 家人用户不能创建、编辑或删除 Post；
- 家人用户不能回答 QA；
- 家人用户不能创建、编辑或删除重大支出记录。

权限控制不应只依赖前端页面隐藏按钮，后端数据访问也必须进行权限判断。

### 12.2 隐私保护

系统中可能包含家庭沟通内容和资金支出信息，因此 V1 阶段应避免保存不必要的敏感数据。

V1 阶段不保存以下信息：

- 银行卡号；
- 身份证件信息；
- 完整交易流水号；
- 详细住址；
- 不适合长期保存的隐私信息。

重大支出记录只保存用于说明支出事项的必要信息。

### 12.3 可维护性

系统应保持清晰的模块边界，便于后续迭代维护。

V1 阶段至少应保证：

- Post、QA、Expenditures 的业务逻辑边界清楚；
- 权限规则集中、明确，避免散落在多个不易维护的位置；
- 文档、设计、任务和测试记录能够相互对应；
- 后续新增功能时，不需要大规模推翻 V1 的基础结构。

### 12.4 可测试性

V1 阶段应具备基础测试能力，尤其是核心业务流程和权限边界。

至少需要验证以下内容：

- 登录与退出流程；
- Public、Family、Owner 的访问边界；
- Post 的创建、查看、编辑和删除；
- QA 的提交、回答和状态变化；
- Expenditures 的创建、查看、编辑和删除；
- Owner 基础管理区的访问控制；
- Dashboard 展示内容符合当前用户权限。

### 12.5 可部署性

V1 最终完成时应具备线上部署结果，并可以通过浏览器访问。

部署结果应满足以下要求：

- 系统可以正常启动；
- 前端页面可以访问；
- 后端服务可以响应核心请求；
- 数据库可以保存和读取核心业务数据；
- 必要的环境变量和部署步骤应有记录；
- 发布阶段应记录线上部署结果。

### 12.6 易用性

V1 面向的主要用户是项目创建者和家人用户，因此界面和流程应尽量直接、清楚。

V1 阶段至少应满足：

- 家人用户登录后能快速看到最近信息；
- 核心页面命名清楚，避免复杂操作路径；
- 提交问题、查看回答、查看支出记录的流程应简单；
- 项目创建者进行内容管理时，不应需要过多重复操作。

### 12.7 性能要求

V1 不面向大规模用户，不设置高并发目标。

在个人和家庭成员小规模使用场景下，系统应保持基本流畅：

- 常规页面加载不应明显卡顿；
- Dashboard 聚合数据不应造成明显等待；
- 常见列表页面应支持按时间倒序展示。

复杂性能优化不纳入 V1 范围。

## 14. 风险与待确认事项

本节记录 V1 阶段可能存在的风险、限制和需要在后续设计或开发过程中进一步确认的事项。

### 14.1 账号创建方式

V1 阶段不提供用户管理页面。家人用户账号由项目创建者通过初始化数据或服务器手动 SQL 方式创建和维护。

后续设计阶段需要细化以下执行方式：

- 初始家人用户账号如何生成；
- 初始密码如何设置和交付；
- 是否需要在首次登录后修改密码；
- 家人忘记密码时，如何通过人工方式重置。

### 14.2 图片与文件上传

V1 阶段暂不提供文件上传功能，因此 Post、QA 和 Expenditures 默认以文本信息为主。

风险：

- 生活近况如果没有图片，表达能力可能较弱；
- 支出记录如果没有凭证附件，透明度会受到一定限制。

处理方式：

- V1 先用文本描述完成核心闭环；
- 图片上传、附件上传和支出凭证功能放入后续版本评估。

### 14.3 支出信息的隐私边界

Expenditures 涉及资金使用信息，具有一定敏感性。V1 需要在“透明”和“隐私保护”之间保持平衡。

V1 阶段采用以下规则：

- 重大支出由 Owner 根据实际情况判断，V1 不设置固定金额阈值；
- 支出记录默认仅 Family 和 Owner 可见；
- V1 不支持单条支出记录设置不同可见范围；
- V1 不允许支出记录向 Public 展示；
- 支出说明中应避免记录银行卡号、完整交易流水号、详细住址、身份证件信息等敏感内容。

V1 默认不向公开访客展示重大支出记录。

### 14.4 QA 可见范围

V1 阶段采用简单 QA 可见范围规则：QA 默认对 Family 和 Owner 可见，对 Public 不可见。

V1 阶段不支持以下能力：

- 单个问题设置独立可见范围；
- 仅提问人和 Owner 可见的问题；
- 问题隐藏；
- 问题归档。

如果后续实际使用中出现隐私需求，再在 V1.1 或后续版本中评估更细粒度的 QA 可见范围。

### 14.5 通知机制缺失

V1 不做邮件、短信、微信或 App 推送通知。

风险：

- 家人可能不知道系统中已有新 Post、新回答或新支出记录；
- 项目创建者可能需要通过其他方式提醒家人查看。

处理方式：

- V1 先采用主动登录查看；
- 通知功能根据实际使用频率在后续版本评估。

### 14.6 部署与运行成本

项目计划作为长期维护的 Web 应用，V1 最终需要具备线上部署结果。云服务会产生一定费用。

风险：

- 数据库、服务器、存储和网络服务可能产生持续成本；
- 正式部署架构如果过早复杂化，会增加维护负担。

处理方式：

- V1 开发阶段优先保证本地环境可运行；
- 正式部署时控制资源规模；
- 云端架构和成本控制在发布阶段单独记录。

### 14.7 需求膨胀风险

本项目具备长期扩展空间，容易在 V1 阶段加入过多功能。

风险：

- V1 开发周期被拉长；
- 核心功能迟迟无法闭环；
- 需求、设计和实现文档失去一致性。

处理方式：

- 严格遵守 V1 不做范围；
- 新想法优先记录到 Backlog；
- 只有影响核心闭环的问题才进入 V1。
