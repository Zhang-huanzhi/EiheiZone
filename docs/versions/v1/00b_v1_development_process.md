## 2. 流程目标与原则

V1 的目标不是套用完整企业流程，而是为个人项目建立足够的工程约束：先冻结范围，再设计边界，将设计拆成可执行任务，通过测试形成证据，最后以真实部署和用户验收结束版本。

执行遵循以下原则：

- **上游先确认**：需求未接受前不冻结设计，设计未接受前不开始正式任务分解；
- **小步可运行**：实现阶段每次完成一个可执行的小步骤并立即验证；
- **证据优先**：完成状态由代码、Migration、测试和运行结果证明，不以“写完了”代替验收；
- **范围受控**：V1 不做事项进入 Backlog，不在实施中隐式扩张；
- **文档分工**：正式文档记录基线和结论，学习笔记记录理解过程，两者不混为一份；
- **变化可追踪**：核心契约变化先更新上游依据，再调整实现和测试。

## 4. 阶段进入与退出规则

### 4.1 需求定义

**进入条件：** 已明确项目背景、目标用户和要解决的问题。

**退出条件：** V1 范围、三类角色、45 条 P0 功能需求、不做范围和验收标准已经接受。技术实现细节不写入需求结论。

### 4.2 架构设计

**进入条件：** `01_v1_requirements.md` 状态为 Accept。

**退出条件：** 权限矩阵、核心对象、数据库结构、API、页面路由、模块职责和本地/生产边界已经明确，足以支持任务分解。局部类名和函数名留到实现阶段。

### 4.3 任务分解

**进入条件：** 需求和设计基线均已接受。

**退出条件：** 11 项任务覆盖基础工程、数据访问、API、前端、认证、三个业务闭环、Dashboard 和系统联调；每项均有完成标准，并保持线性执行顺序。

### 4.4 编码实现

**进入条件：** 当前任务的设计依据、实施内容和验证方法清楚。

**退出条件：** 11 项任务全部完成；系统可以从登录开始演示核心流程；代码、Migration、后端测试、前端测试和 E2E 已形成；可以冻结测试基线。

### 4.5 测试验证

**进入条件：** 功能实现结束、测试环境与开发环境隔离、待测 Git 基线固定。

**退出条件：** 45/45 P0 需求通过；后端 229 项、前端 79 项、Playwright 2 项通过；无未关闭的 V1 功能缺陷；遗留风险已记录并交给发布阶段处置。

### 4.6 部署发布

**进入条件：** 第五阶段测试通过，生产配置、域名、服务器和秘密边界已确认。

**退出条件：** 公网 HTTPS、Owner/Family/Public 核心流程、PWA、Android 真机和 VPS 重启恢复通过；风险已作出 Pass、Accept Risk 或 Deferred 判定；最终状态为 Accept。

## 6. 文档与变更规则

当实施发现上游定义不一致时，不直接让代码成为唯一事实来源，而应按以下顺序处理：

1. 确认变化是否仍属于当前版本范围；
2. 修改受影响的需求或设计基线；
3. 调整任务、实现和自动化测试；
4. 在测试或发布记录中保留修正证据；
5. 重新执行受影响的质量门禁。

局部重构、变量命名和不影响外部契约的文件调整不要求重写正式设计。以下变化必须同步更新长期资产：

| 变化 | 必须更新或新增的产物 |
| --- | --- |
| 角色、权限、核心对象、API 或页面边界变化 | `02_v1_design.md` |
| 数据库 Schema 变化 | 新的 Alembic Migration |
| 框架主干、部署形态或跨模块边界发生重大变化 | ADR 与相关设计文档 |
| 单次小版本功能、验证和发布 | 对应的迭代文档 |

## 7. V1 之后的迭代流程

V1 已于 2026-08-05 冻结。后续 V1.1、V1.2 等版本不再重复建立五份阶段文档，默认使用一份 `iterations/v1.x_xxx.md` 完成四步闭环：

| 步骤 | 需要回答的问题 | 记录内容 |
| --- | --- | --- |
| 1. 迭代定义 | 本次为什么改、明确改什么？ | 目标、范围、不做事项和验收标准 |
| 2. 影响分析 | 会影响哪些权限、数据、API、页面或部署？ | 影响范围、方案和风险 |
| 3. 编码实现 | 代码、Migration 和测试如何落地？ | 实际变更与验证命令 |
| 4. 验证发布 | 是否通过、如何上线、还有什么风险？ | 测试结果、发布记录和遗留事项 |

只有重要设计变化才更新 `02_v1_design.md`；数据库变化必须新增 Migration；重大架构决策新增 ADR。这样既保留 V1 建立的工程约束，也避免个人项目在每次小迭代中重复承担完整文档成本。

## 8. 流程验收结论

六个阶段均已完成，五份正式阶段文档、代码、Migration、自动化测试和部署结果相互可追踪。该流程帮助 V1 控制了需求膨胀，并把“实现完成”“测试通过”和“可以发布”分成不同判定。

这套流程适合当前单人长期维护场景，不应被视为所有项目的固定模板。协作者数量、合规要求、发布频率或系统风险显著增加时，应重新评估代码评审、自动流水线、变更审批和更正式的项目治理方式。
