# ADR-0001：编码代理的协作约定与 Git 边界

## 背景

- 项目原先用 Codex 协作。仓库根目录 `AGENTS.md` 被 `.gitignore` 排除，服务器登录说明放在 `.codex/` 下，并且曾经进入过 Git 历史。切换到 Cursor 之后，这些约定需要在换机器、重新克隆和后续功能开发时仍然有效。

同时，原先的 Git 规则是禁止代理执行任何 Git 命令。实际开发里需要代理查看状态、建立分支并在分支上修改；不受约束地开分支，又会让一次功能散落在多条分支上。

本决定同时影响协作方式、仓库安全和以后每次功能的分支策略，因此单独记录，不只留在一次迭代文档里。

## 候选方案

1. 继续禁止代理执行 Git，需要分支或提交时只把命令交给用户。这样不会产生多余分支，但查看状态、建立分支和保持分支更新都要中断当前工作。
2. 允许代理自由执行 Git，包括为同一次功能连续开多条分支。这样操作少受阻，但分支和提交容易散乱，`main` 也更难保持可发布。
3. 把协作约定抄进 `.cursor/rules`，并继续忽略 `AGENTS.md`。Cursor 可以有自己的规则文件，但会和 `AGENTS.md` 形成两套需要同时维护的说明。
4. 保留 `.codex/server-login.local.md` 作为登录说明路径，即使它已经进过仓库历史。路径继续绑定 Codex，也容易再次被加入提交。



## 决策

采用「仓库内一份可跟踪的 `AGENTS.md`，Git 可以执行，但一次功能只使用一条分支」。

- Cursor 和以后的编码代理都读取仓库根目录 `AGENTS.md`。不另建平行的 `.cursor/rules`。
- `AGENTS.md` 随仓库保存。其中没有主机、密钥或密码。
- 上一级 `EiheiZone/AGENTS.md` 负责 `notes/` 与代码目录的工作区边界。代码仓库内的构建、测试、提交格式和 Git 边界以 `eiheizone/AGENTS.md` 为准。
- 一次功能或一次迭代只从最新 `main` 开一条短期 `feat/`、`fix/` 或 `docs/` 分支，名称与迭代文档一致。后续修改留在这条分支上。合并之后如果继续做，再从 `main` 新开一条。
- 可以查看状态、差异和日志。提交、推送、创建 Pull Request 和合并，要用户明确提出。
- 不使用 force push、hard reset，也不改写已经推送的历史，除非用户明确要求。
- 上一级目录和 `notes/` 不初始化仓库、不提交、不推送，除非用户明确要求。
- 本机服务器登录说明放在 `.local/server-login.md`，由 `.gitignore` 忽略。`.codex/` 一并忽略。用户目录中的模型、代理和命令放行配置不进入仓库。



## 后果

- 克隆仓库后即可得到当前协作约定，不必依赖某台机器上被忽略的 `AGENTS.md`。
- 同一次功能的代码、测试和迭代文档集中在一条分支上。微信通知这类已经合并的工作，若要继续做，从 `main` 另开一条功能分支，不回到已经合并的旧分支上堆叠。
- 代理仍不能在用户未要求时提交、推送或合并，也不能改写已发布历史。
- 合并本决定时，变更包含 `AGENTS.md` 和 `.gitignore`，按现有 CI 规则会运行检查并进入生产部署。生产运行不依赖这两个文件。
- 登录说明已在历史提交 `0fc51b6` 中出现。本决定只阻止它进入后续提交，不清理已有历史。
- 上一级 `EiheiZone/AGENTS.md` 不在代码仓库中。工作区规则要在那份文件里同步，不能只靠本仓库提交带过去。
