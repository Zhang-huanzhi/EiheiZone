# 迭代文档规则

V1 之后，一次功能或一组相关变更默认使用一份迭代文档（模板见 [`_template.md`](_template.md)），不再重复拆分需求、设计、计划、测试和发布多份文档。小错字、局部重构或不改变外部行为的维护，直接写在提交说明与 PR 中即可。

## 1. 状态与裁剪原则

迭代只使用 3 种状态，日期记录进入当前状态的当天（`YYYY-MM-DD`）：

| 状态 | 含义 |
| --- | --- |
| `In Progress` | 分支已创建，正在设计、实现或验证 |
| `Accepted` | 代码、测试与验收标准已完成，版本收口时归档至 `docs/versions/v1.x/` |
| `Deferred` | 暂停推进并移入 `docs/iterations/backlog/`，保留已验证事实，不计入已交付能力 |

文档章节按「3 项必填 + 3 项按需」裁剪，不留空表：

- **开工必填**：`背景与目标`、`范围与不做事项`、`验收标准`。
- **按需保留**：
  - `方案与技术影响`：涉及接口、表结构、Migration、配置、权限或部署变化时填写。存在多种真实实现方式时，用短文或「方案 / 取舍」简表写下为什么选这一种；不要求加权决策矩阵。只有一种合理做法时直接写结论。选择会影响多个模块、部署、安全或数据边界，或以后的迭代还得重做这个决定时，同时新增 [`../adr/`](../adr/README.md) 并在迭代文档中链接。
  - `实现与测试记录`：完成后填写实际结果，只用 `PASS`、`FAIL`、`未验证`。数据库结构变化必须在此记录专用测试库的 Alembic Migration 验证结果。
  - `遗留风险与后续事项`：存在未覆盖边界或标为 `Deferred` 时填写。
