# V1.2 / 002 公网访问问题诊断

## 前言

V1.2 / 001 已经确认，页面慢的主要方向不是业务代码，而是中国大陆客户端访问海外源站时经过的公网路径。本轮把这个判断拆开检查：测源站延迟和丢包，追踪路由，比较 VPN 和 Cloudflare 的访问表现，再看服务器 TCP 参数以及浏览器的连接复用情况。

本轮已经关闭 Cloudflare 的橙色云代理，并根据实际操作记录将服务器 TCP 拥塞控制从 `cubic` 切换为 BBR。没有改动 `backend/`、`frontend/`、数据库，也没有给动态页面或 RSC 请求加缓存。五份原始调查记录和相关图片已经复制到本迭代目录，图片引用也从 Obsidian 格式改成了 docs 可用的相对路径。

## 诊断结论

大陆直连韩国源站时，平均 RTT 约 `300 ms`，同时存在波动性丢包。路由追踪中，国内到韩国运营商节点的延迟约 `75~95 ms`，后面又出现一次明显跳变，最终到源站约 `300 ms`。这更像跨境公网互联质量问题，不像服务器一直处于高负载。

页面使用 HTTP/2，多个 Next.js RSC 请求共用一条连接。网络顺畅时请求可以很快完成；一旦链路丢包，同一条 TCP 连接上的请求会一起等待重传，于是出现数秒到几十秒、个别接近 1 分钟的长尾。

VPN 改变访问路径后，页面明显变快，进一步说明问题主要在客户端到源站之间。现有人工测试没有证明 Cloudflare 免费代理能稳定改善动态页面，所以目前保持关闭。BBR可能减轻丢包造成的传输退化，但不能改变跨境路径本身。

## 原始材料调查小结

### Ping

多组 Ping 结果都显示平均 RTT 接近 `300 ms`：

| 发送数 | 丢失数 | 丢包率 | 平均 RTT |
| ---: | ---: | ---: | ---: |
| 50 | 7 | 14.0% | 299 ms |
| 200 | 14 | 7.0% | 297 ms |
| 500 | 21 | 4.2% | 300 ms |
| 1000 | 37 | 3.7% | 297 ms |

1000 次里丢了 37 个包，实际是 `3.7%`，不是 `37%`。不同样本量的比例不同，说明丢包会随时间变化。Ping 只能说明 ICMP 路径不稳定，不能直接当作 HTTPS/TCP 的精确丢包率，但高延迟这一点已经很明确。

### 路由追踪

路由前段延迟较低，到韩国运营商节点约 `75~95 ms`，之后某一跳升到约 `265 ms`，最终源站约 `300 ms`。可以确认路径中存在明显的延迟跳变，但中间的 `* * *` 也可能只是路由器不回应 ICMP，不能仅凭这份结果断言“绕美国”或锁定具体运营商。

### 人工端到端测试

VPN 开启时，多数页面样本约 `0.5~1.5 s`；VPN 关闭后出现数秒到几十秒的长尾，个别 RSC 请求接近 1 分钟。Cloudflare 开关前后没有出现稳定、可重复的改善。测试中缓存开关和网络状态并不完全一致，因此这些结果用于判断方向，不作为严格的性能对照实验。

### TCP 算法

原始检查结果为：

```text
net.ipv4.tcp_congestion_control = cubic
```

服务器后来已经切换到 BBR。BBR更适合这种高延迟、偶发丢包的长连接，但目前没有切换后的运行值和同条件页面数据，所以这里只记录已经做过这项调整，不把改善幅度写成结论。

### F12 Protocol

请求的 `Protocol` 为 `h2`，多个请求使用相同的 `Connection ID`，说明 HTTP/2 多路复用正常，没有因为重复握手产生额外开销。它能减少连接建立次数，却不能消除共享 TCP 连接在丢包时的等待。

## 分析

五份材料合在一起，问题链条比较清楚：

```text
跨境公网路径高 RTT、偶发丢包
        ↓
TCP 重传，cubic 可能进一步降低发送速率
        ↓
多个 RSC 请求共用一条 HTTP/2 连接
        ↓
最慢请求拖住页面，形成长尾
```

所以，当前最主要的瓶颈仍然是“大陆用户到韩国源站的访问路径”。BBR可以缓解传输层影响，减少请求和静态缓存可以减少放大效应，但这些措施都不能替代更好的网络入口或源站线路。

## 优化方案

### BBR

BBR是已经做过的低成本调整，不需要修改业务代码。它主要用于减轻丢包后的吞吐下降和重传等待，适合作为现有服务器配置保留。它能缓解问题，但不等于解决了跨境路径问题。

### 腾讯云 EdgeOne

EdgeOne可以作为 Cloudflare 之外的一个可选方案。它的思路是让大陆用户先接入边缘节点，再由云厂商网络回源韩国源站；公开静态资源可以在边缘缓存，用户与边缘之间也可以使用更适合弱网的协议。

它适合不迁移现有服务器、但希望改变用户接入路径的场景。实际效果会受节点、回源线路、套餐、域名条件和产品配置影响，因此这里只把它作为方案记录，不把它视为已经执行或必然有效的改动。

### 更换源站地域或线路

将源站放到香港、日本，或更适合大陆访问的线路，通常比继续调整 Cloudflare 规则更直接地降低 RTT 和丢包风险。这类方案一般不需要改业务代码，但会带来服务器迁移、数据迁移和费用方面的变化。

### 静态资源 CDN

JS、CSS、字体和公开图片可以交给 CDN 或边缘缓存，减少每次访问都回源韩国的请求量。登录态页面、API 和 RSC 请求不适合直接套用同一套缓存规则。

### 应用层缓解

如果网络入口暂时不变，还可以减少不必要的 RSC/接口请求，并增加超时、重试和降级状态。这些做法不能降低物理 RTT，但能减少单个慢请求对整页体验的影响，实施时才需要改 `backend/` 或 `frontend/`。

### Cloudflare 的适用范围

Cloudflare DNS 可以继续保留，但按本轮结果，不把免费橙色云代理作为大陆访问韩国动态页面的主要加速手段，也不缓存登录态页面、API 或 RSC。它仍然适合海外访问、证书、基础防护和静态资源分发。
