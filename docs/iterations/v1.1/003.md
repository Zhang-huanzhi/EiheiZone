# 迭代任务 003：基于 GitHub + SSH 的最小可用 CI/CD

## 状态

已完成（2026-08-11）。仓库、GitHub 与生产服务器配置已落地，自动部署、分支保护负向验证、回滚及回滚后恢复均已完成。

## 目标

为单台 Linux 云服务器建立低维护成本的发布链路：Pull Request 先通过 CI；`main` 的 CI 成功后，GitHub Actions 通过 SSH 调用服务器上的固定脚本；部署脚本更新代码、构建 Compose 服务并执行健康检查。

## 已核实的项目现状

- 后端为 FastAPI，使用 Python 3.14、uv、Ruff 和 pytest。
- 前端为 Next.js 16，使用 Node.js 22、npm、ESLint、Vitest 和 TypeScript。
- 生产环境采用 Docker Compose，包含 PostgreSQL、FastAPI、Next.js 和 Caddy。
- 健康检查入口已存在：`GET /api/v1/health`，同时检查数据库连通性。
- 生产发布分支为 `main`，服务器项目目录固定为 `/opt/eiheizone`。

## 实现

### CI

`.github/workflows/ci.yml` 在 Pull Request 及 `main` push 时先运行两个并行 Job：

- Backend：启动独立的 PostgreSQL 17 测试服务、锁定安装依赖、Ruff、Alembic migration、pytest。
- Frontend：锁定安装依赖、ESLint、Vitest、TypeScript 类型检查、生产构建。

两者成功后运行 Deployment artifacts Job：校验 Bash 语法及 Compose 配置，并按生产 Dockerfile 构建前后端镜像。

workflow 只授予仓库内容读取权限；同一引用的新运行会取消旧运行。

### CD

`.github/workflows/deploy.yml` 仅在以下情况部署：

- `main` 的 push 所触发的 CI 成功完成；
- 有权限的维护者手动执行 `workflow_dispatch`。

生产部署使用 GitHub Environment `production`，同一时间只允许一个部署运行。Actions Runner 使用固定 known_hosts 连接服务器，并执行：

```bash
bash /opt/eiheizone/deploy.sh
```

### 部署与回滚

`deploy.sh` 固定发布 `/opt/eiheizone` 的 `main`：

1. 检查命令、Git 仓库、`.env` 和工作区状态。
2. 使用文件锁拒绝并发部署或回滚。
3. 从 `origin/main` 进行 fast-forward 更新。
4. 以目标 commit SHA 标记前后端镜像，并执行 `docker compose up --wait`。
5. 请求 `https://eihei.zone/api/v1/health`。
6. 健康检查成功后记录当前及上一稳定 commit。

失败时脚本返回非零状态并输出上一稳定 commit 的回滚命令。脚本不会自动回滚，避免在迁移或基础设施故障时反复修改生产状态。

默认回滚到上一稳定版本：

```bash
bash /opt/eiheizone/rollback.sh
```

也可指定一个属于 `origin/main` 历史的完整 commit SHA：

```bash
bash /opt/eiheizone/rollback.sh <40-character-commit-sha>
```

部署状态只保存在服务器的 `/opt/eiheizone/.deploy/`，该目录已被 Git 忽略。当前和上一稳定版本的前后端镜像分别以完整 commit SHA 标记；正常部署成功后清理更早的镜像。回滚优先复用已验证的稳定镜像，镜像不存在时才从目标 commit 重新构建。Compose named volumes 不会因代码回滚而删除。

## 首次配置

### 服务器

服务器需安装 Git、curl、flock、Docker Engine 及支持 `--wait` 的 Docker Compose v2，并保证部署用户可执行 Docker：

```bash
sudo mkdir -p /opt/eiheizone
sudo chown ubuntu:ubuntu /opt/eiheizone
git clone https://github.com/Zhang-huanzhi/EiheiZone.git /opt/eiheizone
cd /opt/eiheizone
cp deploy.env.example .env
# 编辑 .env 并替换全部占位值，然后进行首次人工启动和健康检查。
docker compose up -d --build --wait --wait-timeout 180
curl --fail https://eihei.zone/api/v1/health
```

部署用户只需 GitHub 仓库读取权限和 `/opt/eiheizone`、Docker 的必要权限，不应授予无关目录的写权限。

### GitHub

在仓库中创建 `production` Environment，并添加以下 Secrets：

| Secret | 内容 |
| --- | --- |
| `SSH_HOST` | `150.109.241.217` |
| `SSH_PORT` | SSH 端口，例如 `22` |
| `SSH_USER` | `ubuntu` |
| `SSH_PRIVATE_KEY` | 专用于部署的私钥，不得复用个人私钥 |
| `SSH_KNOWN_HOSTS` | 预先核对的服务器 SSH host key 记录 |

`SSH_KNOWN_HOSTS` 应在可信渠道核对服务器指纹后生成，不能在每次 workflow 中临时执行 `ssh-keyscan`，否则无法可靠识别中间人攻击。

为 `main` 设置分支保护规则：

- 禁止直接 push，要求 Pull Request。
- 要求 `Backend`、`Frontend` 与 `Deployment artifacts` 状态检查成功。
- 要求分支与最新 `main` 同步后才能合并。
- 禁止强制 push 和删除分支。

生产业务环境变量仅保存在服务器 `/opt/eiheizone/.env`。GitHub 只保存建立 SSH 连接所需的 Secrets。

## 边界与风险

- 第一版只支持一台 Linux 服务器，不包含灰度、多机编排和自动流量切换。
- 回滚只恢复代码和容器镜像构建结果，不会逆向执行 Alembic migration。数据库变更必须保持向后兼容，破坏性迁移需另行设计恢复方案。
- 数据库和媒体数据仍位于服务器 named volumes；异机备份不属于本迭代，但主机故障仍可能导致数据丢失。
- GitHub Environment、Secrets、分支保护、服务器权限、首次部署和回滚演练属于外部配置；仓库被迁移或复制后必须重新建立这些配置。
