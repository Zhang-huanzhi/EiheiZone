## 1. 目标

为 VPS 整机、磁盘或误操作故障提供可恢复的异地备份。每天备份 PostgreSQL 与 Post 图片，使用客户端加密后上传腾讯云 COS，保留最近 7 份，并记录隔离恢复步骤。

## 2. 范围

- 增加由服务器 cron 每日调用的备份脚本；备份快照期间短暂停止 backend 写入，完成本地快照后立即恢复服务，再进行 COS 上传。
- 使用 `rclone` Tencent COS S3 后端及 `crypt` remote；不接入 Google Drive/OAuth，不修改应用存储方式或数据库结构。
- 更新运维手册，说明 COS 控制台准备、VPS 密钥配置、日志检查和新服务器恢复步骤。
- 通过模拟测试覆盖服务恢复、上传失败和保留策略；不增加自动告警。

## 3. 不做事项

- 不提供高可用、跨云冗余、数据库复制或自动故障切换。
- 不将生产 `.env`、COS 凭证、加密密码、真实家庭数据或备份文件提交到 Git。
- 不由迭代实现者创建腾讯云资源或保管用户的 COS/加密密钥；用户在控制台创建 COS 桶和受限访问凭证。

## 4. 技术方案

- 使用首尔地域的私有标准存储桶。通过单独的 `rclone` 配置连接 COS 和加密 remote；密钥及加密参数保存在服务器仅 root 可读的配置中。
- 脚本创建权限为 `0700` 的本地临时目录，导出 PostgreSQL custom dump 并归档 `media_data` 图片，同时生成校验和。仅当数据库和图片快照均完成后恢复 backend 并等待健康检查，然后上传加密归档。
- 备份以日期标识；远端上传及校验成功后才清理超过最近 7 份的旧备份。失败时返回非零状态、保留本地快照和旧远端备份。清理本地明文材料仅发生在上传校验成功后。
- 服务器以韩国时间每日 03:00 运行。日志供人工检查；不配置告警。
- 恢复手册要求使用新的空数据库和独立 media volume，在隔离环境恢复数据库与图片、验证 Alembic 状态和内容对应关系后再切换服务。

## 5. 验收标准

1. 在无真实凭证的模拟环境中，快照期间停止 backend，快照后恢复 backend 并通过健康检查；任何失败路径都尝试重新启动 backend。
2. 模拟 COS 上传失败时脚本返回失败，保留本地恢复材料和所有旧备份；上传和校验成功后只保留最新 7 份。
3. CI 能运行脚本语法检查和模拟测试，不访问生产服务器或真实 COS。
4. 用户在腾讯云控制台完成账号按量计费确认、私有 COS 桶及受限访问凭证设置后，用虚构文件验证上传、下载和客户端解密。
5. 在隔离环境恢复一份真实备份，验证迁移状态、家庭内容和 Post 图片对应关系，并在本文记录实际结果与遗留风险。

## 7. 遗留风险

本迭代已转入延期池，以下内容仍未完成，不能作为 v1.4 的持续运行能力声明：

- 备份失败通过服务器日志发现，没有自动告警。
- COS 与 VPS 同属腾讯云，无法覆盖腾讯云账号或平台级故障。
- 加密密码遗失会导致备份不可恢复，必须独立保存。
- 实际费用取决于备份体积、地域和恢复流量，以腾讯云控制台账单及预估为准。
- 2026-10-27 第一次手工备份时，脚本执行 `docker compose up` 且未带 `DEPLOY_IMAGE_TAG`，把 backend 重建成旧的 `latest` 镜像并短暂不可用。已改回当时的生产镜像 `44b5d77e17fdc85b3384134b4e4f6394861ee031` 并确认健康。脚本已改为 `--no-recreate`，并用下载后 `cmp` 校验单个归档；这两处改动在 `fix/v1.4-006-backup-restart`，尚未进入 `main`。在该修复随部署到达服务器之前，不要安装每日 cron。
- 每日 cron 尚未安装，备份没有持续运行。2026-10-27 的手工备份和隔离恢复只是一次演练。账号持有人暂不继续推进备份，等理解当前步骤并确实需要时，再安装每日任务。

后续继续实施时，应新建目标版本迭代和分支，先部署脚本修复，再安装 cron，最后补充持续运行、失败告警和恢复验收证据。
